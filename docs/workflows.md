# Workflow recipes

Step-by-step command sequences for the workflows routed from `CLAUDE.md`. The GOGPT Editing Manual is authoritative for research rules; the SOPs (`docs/sops/`) are the operational rules; this file is the glue — which commands, in which order. Read the section for the workflow you're running, plus the relevant SOP(s).

**Fresh-pull shorthand used throughout** (from `scripts/`):

```
python ../../gem-db-ops/gogpt/pull.py --output gem_export_gogpt.csv
python pull_gem_db.py --map-only
python scope_filter.py
```

→ fresh all-combustion CSV (~35k rows, 91 cols) + column-index map (`gem_export_gogpt.csv.colmap.json`) + GOGPT-scoped CSV (`gem_export_gogpt_scoped.csv`). The pull engine lives ONLY in the sibling `../gem-db-ops` repo; auth via `GEM_READONLY_DB_URL`. **Re-derive the colmap every run** — the schema can drift; `--map-only` errors loudly on missing/unknown columns (escalate drift to the user). `scope_filter.py` uses the authoritative `trackerSearch='GOGPT'` DB query when `GEM_READONLY_DB_URL` is set, else pass `--offline` for the fuel heuristic (weaker — note it in the batch record). **Keep the unfiltered CSV**: conversion/replacement checks need the coal/bioenergy side (shared plants, R-suffix replacement units, timepoint links).

**How the workflows fit together.** Triage is the forward-looking chooser — `worklist.py` + the inferred-status sweep produce a *memo* recommending what to work. The doers turn a chosen scope into the actions/evidence *deliverable pair*: Update (§2) and Discovery (§3). QC (§5) is the backward-looking checker — memo + validation report, fixes route back into Update ("QC detects, Update fixes"). The campaign roster (§6) is the quarterly bookkeeping wrapper around all of it. So: **Triage (memo) → Update / Discovery (deliverables) → QC (memo → back to Update)**, inside a `campaigns/<quarter>/` cycle.

**Model selection (who runs on what).** Subagent model choice follows the global dispatch-time rule (user-level CLAUDE.md — cheapest model genuinely good enough, chosen per dispatch, never pinned). In this repo the judgment-heavy work that stays in the top-tier main loop: scope calls, threshold/scope-gate judgments on discovery candidates, escalations, and the pre-build QC gate on any subagent output. Mechanical fan-out (per-plant source sweeps from a clear brief, URL verification passes, per-country worklist summarization) can go down-tier. The location step (`docs/reference/location.md`) is split the same way: address search, geocoding and the satellite look run inside the Sonnet or Haiku sweep; only the plants it hands back as needing a map georeferenced or a site call go to a short Opus or Fable pass (Baird 2026-10-20). Subagent output is never pre-trusted regardless of model — `qc_checks.py --staged`, the gem.wiki/banned-domain scan, and a URL spot-check run the same either way.

**Batch artifact conventions.** Per-batch staging JSON lives in `batches/<scope>/staging/` (`staged_<lane>.json`, lanes and record shapes in `docs/reference/staged_json_schema.md`) — committed as the audit trail. When a scope runs a second mode in the same cycle (e.g. a discovery pass after an update batch), stage it in a separate per-mode dir — `batches/<scope>/staging-discovery/` — so the build doesn't re-include the other mode's lanes; point `--staging-dir` and `URL_VERIFIER_LOG` there. Deliverables land in `batches/<scope>/deliverables/` named `gogpt_batch_<YYYYMMDD>_<HHMM>_ET_<scope>_<mode>_{actions.xlsx,evidence.md}` (stamp via `TZ=America/New_York date "+%Y%m%d_%H%M_ET"`; naming rules in `docs/reference/workbook_conventions.md`; xlsx gitignored, evidence md committed; never overwrite). When running `url_verifier.py`, export `URL_VERIFIER_LOG=<path into the batch's staging dir>` so every verification attempt lands in an append-only JSONL next to the staged JSON. Each batch gets one line in `batches/<scope>/INDEX.md` and (for cross-scope runs) a small md in `batches/run_records/`.

## §1 Fresh pull + scope filter (start of every batch)

1. Fresh-pull shorthand above. Confirm: CSV mtime changed, `--map-only` reports 86/86 known columns, scope filter prints kept/dropped counts (scoped view ≈ oil+gas only).
2. If the pull fails on auth, ask the user to check `GEM_READONLY_DB_URL` (see `env.example`); never fall back to a stale CSV silently. `worklist.py` and `build_state_brief.py` stop when the scoped CSV or the full export is over a day old (`paths.require_fresh_export`), and say so when a newer pull landed in gem-db-ops because `--output` was left off; `--allow-stale-export` is only for a deliberate rebuild of an earlier batch.
3. For triage-only sessions this section plus §4 is the whole recipe.

## §2 Update existing plants (most common)

1. Fresh pull (§1).
2. Confirm scope per Update SOP §2 — which country/countries (usually the quarter's assignment from `campaigns/<quarter>/roster.csv`), whether Data-Source backfill is in scope. Create `batches/<scope>/staging/` if new.
3. `python worklist.py --country "<Country>"` → the priority-ordered worklist (`work/worklist_<tag>.csv`): in-development first, then shelved review, planned retirement this year, planned retirement any year, the rest; 2y/4y inferred-status candidates flagged (the 4y test only on announced, pre-construction and construction units, counted from the Latest Activity date). Work it top-down. For a full-country assignment, the ladder sets priority but not coverage — after it's exhausted, sweep the remaining status groups in the upstream session order (new proposals, then in-development, then shelved and cancelled, then operating, then retired and mothballed) per Update SOP §3. Then `python validation_report.py --country "<Country>"` (or `--state <State>`) → `work/validation_<tag>.md` + `.json`: the GOGPT Validation Report errors stored in the DB (checklist row 7), each sorted into a research fix, a by-hand web UI fix, or the manual's optional coal exception (a project-level error on a plant that also has coal units, a unit-level error on a coal-to-gas conversion; the gate accepts "optional under the manual" for those). Fold the fixes into the worklist (Update SOP §3.6); every fix and person item gets an answer tagged with check 7 before the build, and `state_gate.py` (gate `validation`) checks that against a validation file under a day old.
4. **Cross-cutting scans** (adopted from the upstream pipeline — CLAUDE.md "Upstream"): `python export_to_dump.py` bridges the fresh scoped CSV into `upstream/gogpt-tracker/data/`, then from `upstream/gogpt-tracker/scripts/`:
   - `python3 gogpt_csv_query.py --country "<Country>" --counts-only` — unit-counts baseline; reconcile a mismatch vs the roster/assignments tab before researching.
   - `... --status operating --ownership-scan`, `... --in-progress-scan`, `... --duplicate-scan` — candidates fold into the worklist as extra rows/notes. Scans surface candidates only; nothing is staged from a scan without the normal research + verification path.
   - `... --possible-updates [--pu-file <file>]` — the country's backlog rows (input to step 5c; takes the local CSV or a flattened Drive read of the live sheet).
5. Per plant/unit on the worklist:
   a. Source-search per Update SOP §4, using `docs/reference/source_roster.md` (tiering) and `docs/country_notes/<country>.md`. Harvest the record's EXISTING Data Source cells first — re-verifying a known-good source beats finding a new one (`confidence_tiers.md`).
   b. Apply lifecycle rules per `docs/reference/lifecycle_rules.md` — status vocab, start-year/retired-year logic, the 2020-forward rule, inferred 2y/4y arithmetic.
   c. Check the possible-updates backlog rows for this country (sheet ID in `sop_pointers.md`) and fold them into the same batch.
   d. Conversion/replacement checks against the UNFILTERED export — a gas unit replacing a coal unit at a shared plant needs the GCPT side read (unit_conventions.md, R-suffix + timepoint rules).
   d2. A plant whose location is approximate or blank gets the location ladder (`docs/reference/location.md`). Exact follows the manual's five routes, none of which needs imagery: coordinates published by a government body, operator or owner; coordinates in a permit application or similar document; a map embedded on the owner's or operator's site; Wikimapia or OpenStreetMap; a project Google Maps identifies by name. The satellite look and a georeferenced official map are extra routes. A proposed plant with only a city gets an approximate point in an open area near the city. City, Local area, Major area and Subnational are filled when blank on every plant in scope, exact plants included (an exact plant's coordinates are not reopened). The 500 m move check is a review flag, never a block. Every coordinate a person reads is a Google Maps link.
   e. Stage findings as `staged_updates.json` (+ `staged_qa.json` / `staged_entity.json` / `staged_monitor.json` as needed) per `staged_json_schema.md`. Project-level fields: set `applies_to_all_units` + `sibling_unit_ids`. Number Of Engines and Capacity Per Engine are filled for internal combustion sets and aeroderivative gas turbine sets; a frame gas turbine is one turbine per unit with its capacity in Capacity (MW). Captive fields are filled for every captive plant, including one that exports, with Captive non-industry use recording the export (power, heat, both, none).
6. `python url_verifier.py "<url>" "<claimed value>" ...` on every URL before it enters a staged record; record the verification result in the record's `verifications`.
7. `python entity_lookup.py "<owner name>"` before staging any new owner/operator/parent (entities are shared across trackers and countries; a match anywhere = reuse the existing entity ID).
8. `python qc_checks.py --staged batches/<scope>/staging/staged_updates.json` (and each other lane file) → must exit 0. Fix errors in the staging JSON, not by relaxing the checker.
9. From `scripts/`: `python build_review_package.py --staging-dir ../batches/<scope>/staging --scope <scope> --mode update --output-dir ../batches/<scope>/deliverables` (use `--dry-run` first) → actions xlsx + evidence md.
10. `python recalc.py ../batches/<scope>/deliverables/<actions.xlsx>` → zero formula errors.
11. Add the INDEX.md line, update the campaign roster's `packet_file`, `present_files`.

## §3 Discover new plants/units

1. Fresh pull (§1). Confirm parameters per Discovery SOP §2 (region/country; threshold reminders: ≥50 MW electrical nameplate, EU+UK ≥20 MW; backup engine fleets at data centers count, summed).
2. **First standing input: the captive-power backlog** — `notes/backlog_captive_power_candidates.md` points at candidate JSONs in the sibling LNG repo. Dedup the lists against each other and against the scoped export before any web research (steps in that file).
3. Sweeps per Discovery SOP: country regulator (country_notes + source_roster), trade press, sponsor IR. A candidate is an add on one verified source that names the project, places it in scope and gives a capacity or none (Discovery SOP §3.1, Baird 2026-10-23); the status comes from the manual's ladder.
4. Dedup every candidate against the scoped export (GEM unit ID, name+coords) AND the unfiltered export (the plant may already exist with only coal units — then it's `newunits` on the existing plant, not `newplants`).
5. Screen: capacity threshold on electrical nameplate MW only (never shaft/mechanical-drive), with a data center's backup engine fleet summed (Discovery SOP §3.1; `python data_center_fleets.py` lists the sites); scope fuels per `controlled_vocab.md`. A new plant's coordinates come from the location ladder (`docs/reference/location.md`): an address or site sentence geocoded and checked in imagery earns `exact`, a town alone is `approximate`. Passing candidates → `staged_newplants.json` (nested units) / `staged_newunits.json`; the seven watch cases (under threshold, no generation named, drive or storage unresolved, possible duplicate, plan option, other scope, nothing verified) → `staged_monitor.json` with `watch_case` and `recheck_by`, never discarded.
6. `url_verifier.py` on all URLs; `entity_lookup.py` on every new entity name.
7. `qc_checks.py --staged` on every lane file → exit 0; then build + recalc + INDEX.md as §2 steps 8–10 with `--mode discovery`.

## §4 Triage (decide what to work on)

1. Fresh pull (§1).
2. `python worklist.py --all` (or per candidate country) → per-country priority counts + the inferred-status sweep (shelved-inferred ≥2y, cancelled-inferred ≥4y candidates with their evidence ages).
3. Pull triage inputs per Triage SOP §3: the worklist, the quarter's roster state (`campaigns/<quarter>/roster.csv` — what's assigned/unworked), the possible-updates backlog volume per country, the captive-power backlog status, recent-quarter news signal.
4. Produce a triage memo (markdown, not a deliverable): `batches/triage_<stamp>_ET.md` — recommended batch composition, each option naming the workflow and scope. The user decides before any batch starts.

## §5 Quality control (QC pass / country close-out)

Memo only; stages no edits. Full rules in the QC SOP — including the GC/Country checklist + validation report required before a roster row moves to `done`.

1. Fresh pull (§1) — for a post-apply check the pull must postdate the user's apply.
2. **Mechanical integrity**: `python qc_checks.py --csv gem_export_gogpt_scoped.csv --country "<Country>"` → vocab/threshold/year-logic/ownership violations in the live data.
3. **Citation spot-check**: re-verify a stratified sample of existing Data Source URLs via `url_verifier.py` (dead / bot-blocked / value-missing verdicts). >25% dead in a country → recommend a Data-Source backfill Update there.
4. **Accuracy spot-check** (agent-driven): ~20 unit sample (recently-edited, high-capacity operating, in-development); re-verify Status/Capacity/Fuel/Owner against cited refs + one fresh corroboration each. >10% unsupported → systemic flag, stop and discuss.
5. **Post-apply check**: diff the batch's staged values against the fresh export — applied / not-applied / diverged per edit.
6. Memo to `batches/qc_<stamp>_ET.md`; for a close-out, `python validation_report.py --country "<Country>" --closeout` (or `--state`) must print CLOSE-OUT CLEAN (only the coal exceptions may remain; it reads the live DB, so run it after the apply), `python no_tracker.py --country "<Country>"` (or `--state`) must list nothing live (checklist row 56), `python assigned_comments.py --country "<Country>" --closeout` (or `--state`) must print COMMENTS CLEAN, attach the memos per QC SOP and update the roster row. Stop and ask before spinning up recommended follow-ups.

## §6 Campaign roster refresh (quarterly cycle)

1. New quarter: create `campaigns/<quarter>/` (copy the README from the prior quarter, update the slug).
2. Fresh pull (§1), then `python build_campaign_roster.py --campaign <quarter>` → `campaigns/<quarter>/roster.csv` (per-scope in-development/status counts, US split per state, sorted by in-dev volume; the manual columns `assignee_role`/`assignment_status`/`packet_file`/`applied`/`notes` survive refreshes).
3. Mirror the quarter's "Researcher Country Assignments" tab (link in `sop_pointers.md`) into `assignee_role` — names are fine (ruling 2026-09-15). For US rows the tab is per state (`United States - <State>`); the roster has one row per state under its `scope` key, so match on that (`campaigns/q4-2026/README.md`).
4. Re-run step 2 anytime mid-quarter to refresh counts; roster edits beyond the manual columns belong in the generator, not the CSV.

## §7 Scope sweep (US state or country)

Per-plant agent research for one scope: a US state or a whole country; contract, shard shape and gate in `notes/us_state_agent_plan.md`. Modes: `blind` (calibration, GEM values withheld) or `update` (normal batch). The scope travels as a `where` object (`kind`, `name`, `slug`, `country`, `postal`) from `briefs/_index.json` through `staging/sweep_args.json` into the workflow and the staged records' `meta.scope`. Batch dir and tag: `batches/us-<st>/` for a state, `batches/<country-slug>/` for a country (`germany`, `united-kingdom`).

1. Fresh pull (§1), then from `scripts/`: `python worklist.py --state <State> --all` or `python worklist.py --country "<Country>"`. Write or refresh the note first (`docs/country_notes/united_states/<state>.md` or `docs/country_notes/<slug>.md`); it is inlined into every brief. Read the possible-updates sheet rows for the scope and the upstream scans (§2) and put the ones worth a task into `batches/<tag>/extra_tasks.json` (`{"<L...>": [{"text": ..., "fields": [exact headers]}], "*": [...]}`). Then `python validation_report.py --state <State>` (or `--country "<Country>"`) → `work/validation_<tag>.json` + `.md` (checklist row 7), and `python no_tracker.py --state <State>` (or `--country`) → `work/no_tracker_<tag>.json` + `.md` (checklist row 56: the combustion units the DB could not assign to a tracker for want of a primary fuel; they are absent from every export, so each live one is a web-UI fuel fix for the human), and `python assigned_comments.py --state <State>` (or `--country`) → `work/comments_<tag>.json` + `.md` (the database's Assigned Comments threads on the scope's plants, open first; each open thread becomes an `extra_tasks.json` task, and completed ones are read for leads such as a link nobody followed up). **US states only:** `python match_ids.py --state <State>` → `work/ids_us-<st>.json` + `.md` (checklist row 38). It joins every GEM plant to the EIA-860M file on disk (`eia860m.py --check` keeps `work/eia/` current; a new file comes out about monthly), the EIP sheet's newest "data filtered" tab and the Sierra Club "MATCHED IDs" tab (reference only, never cited), both read through the work gws profile and cached a week under `work/ids/` (`--refresh` to re-read). The memo lists IDs to type into Other IDs by hand (no Data Source goes with an ID, and staging has no Other IDs lane), the EIP and Sierra Club sheet rows whose GEM ID columns are blank for Baird to paste, possible new plants (leads only; ones already in a staging folder are marked), and problems such as a code the file no longer carries. **US states only, the IRP step:** `python irp_sheet.py --state <State> [--state ...] --save-json ../work/irp_tab.json` → `work/irp_us-<state-slug>.json` + `.md` (checklist rows 34 and 37). It reads the "US IRPs" tab of the Update sheet through the work gws profile (one row per utility: plan year, plan links, a running Notes log, draft flag), matches each utility to the state's GEM plants by owner, operator, parent and the "IRP" placeholder plant names, reads the export's `IRP` column (the database's IRP checkbox, yes or no) to list the units already ticked, and writes one whole-plant task per plant a plan can plausibly move. A state with no rows on the tab is marked skipped. `--from-json work/irp_tab.json` reruns offline; the saved tab holds a colleague's notes and stays under `work/`. A draft plan counts (Baird 2026-10-07): a gas project in a draft IRP is enough to add it. **Every scope, the captive LNG step:** `python captive_lng.py --state <State>` (or `--country "<Country>"`) → `work/captive_<tag>.json` + `.md` (checklist rows 6 and 44, and row 39 for a US state). It downloads the captive LNG workbook and the LNG tracker download it was built from (both xlsx, through the work gws profile into `work/captive/`, kept a week; `--refresh` re-reads, `--from-dir` reruns offline), joins the sheet's rows to the tracker by Terminal ID (the tracker's Project ID, so the tracker gives each row its state, country, status, owner, coordinates and the captive GEM plant the LNG team already linked), keeps the scope's rows, and matches each to the scope's GEM plants: by the tracker's captive plant ID, by a plant name with LNG in it, or by location. A matched plant gets a whole-plant task; a qualifying terminal with no plant is a new-plant candidate for the scope-wide agent; the sheet's Excluded rows are listed as do-not-add; GEM plants that look like LNG captive plants but have no sheet row are listed for the LNG team. The workbook is a lead list: its Qualifying rows are checked first, but any verified captive LNG plant at the add threshold (50 MW, or 20 MW in the EU and UK) is an add (Baird 2026-10-27). A row the sheet qualifies on compressor-drive turbines alone is flagged `mechanical_only`: GEM records electrical nameplate only, so the agent has to find generator sets before adding anything. **Every scope, the data center step (Baird 2026-10-27; `notes/data_center_backup_plan.md`):** run it right after the permit harvest (step 3 below) and before `build_state_brief.py`: `python data_center_fleets.py --state <State>` (or `--country "<Country>"`) → `work/permits/<tag>/_data_centers.md` + `.json`, one row per data center site with the generators summed in electrical MW, the permit numbers and a verdict. A backup engine fleet at the summed nameplate threshold (50 MW, 20 MW in the EU and UK) is an add, as is a gas-fired data center plant; capacity unknown means add with capacity blank. Name it "<Operator> <Place> Data Center power station", internal combustion, Backup Power yes, the data center in Project Links. **Every scope, the location step (built 2026-10-20; `docs/reference/location.md`):** `python location_candidates.py --state <State>` (or `--country "<Country>"`) → `work/location_<tag>.json` + `.md`: the plants whose `Location accuracy` is approximate or whose coordinates are blank (never an exact plant), each with its current point as a map link, the place fields it has, and every dataset point with its distance (EIA-860M and the EIA-860 annual Plant table's street address for a US state, permit-portal hits with coordinates anywhere). **Every scope, the existing-link check (built 2026-10-23):** `python check_existing_links.py --state <State>` (or `--country "<Country>"`) → `batches/<tag>/existing_links.json` + `.md`. Every Data Source link already in the export goes through `fetch.py`, and every dead one gets a Wayback lookup for its exact address. A dead link whose saved copy still states the value is staged as a saved-copy record in `staging/staged_updates.json` (idempotent; this replaces `stage_saved_copies.py`); a dead link with no saved copy, and a blocked one, become brief tasks through `--existing-links`. Results are cached a week in `work/existing_links_cache.json` (`--refresh` ignores it; `--dry-run` writes the report only). **Every scope, the statewide source list:** write `docs/coverage/<tag>.json` before the sweep, one entry per statewide source the scope-wide agent must search (`id`, `name`, `url`, `what`: permit notices and permit board minutes, the utility commission's dockets, each grid operator's queue, EIA-860M and EIA-860 for a US state, the utilities' plan and news pages, the possible-updates sheet, the captive LNG sheet, known data centers). `docs/coverage/us-ms.json` is the model.
2. `python build_state_brief.py --state <State> --mode update --extra-tasks ../batches/us-<st>/extra_tasks.json --validation ../work/validation_us-<st>.json --ids ../work/ids_us-<st>.json --irp ../work/irp_us-<state-slug>.json --captive ../work/captive_us-<state-slug>.json` (or `--country "<Country>"` with `../work/validation_<country-slug>.json`, `--captive ../work/captive_<country-slug>.json` and no `--ids`/`--irp`) → `batches/<tag>/briefs/`. `--irp` puts the plan task on each matched plant's brief, writes `briefs/_irp.md` (the per-utility block the scope-wide agent reads: plan links, latest tab note, matched plants, units already ticked) and an `irp` entry in `_index.json` (plan links, ticked units, skipped flag). `--captive` puts the sheet task on each matched plant's brief (checks 6 and 44), writes `briefs/_captive.md` for the scope-wide agent (the matched terminals, the qualifying terminals GEM lacks with the tracker's owner and coordinates and the sheet's sources, and the excluded ones, which are leads to check, not do-not-add) and a `captive` entry in `_index.json` (terminals with their matched plant IDs, new candidates). `--data-centers ../work/permits/<tag>/_data_centers.json` (every scope) puts a task on each GEM data center plant and writes every site at the threshold into `briefs/_scope.md` as a named add task; every site at or above the threshold, or with generators and unknown capacity, must be answered in `batches/<tag>/coverage.json` under `data_centers`, and `state_gate.py` gate `data-centers` enforces it. `--existing-links ../batches/<tag>/existing_links.json` (every scope) puts a "links already in the database that are gone" block on each plant with a dead or blocked link and no verified saved copy, and that plant is in ladder scope. `--ids` also writes every EIA plant the matcher lists as missing from GEM into `briefs/_scope.md` (with the statewide source list) and into `_index.json` as `ids_followup`, so each one is a named task for the scope-wide agent. `--location ../work/location_<tag>.json` (every scope) puts the location ladder task on each candidate plant's brief (row 25, and row 42 for an operating plant): the current point as a map link, the dataset points and distances, and the address when a dataset gives one. `--promote <staging dir>` (repeatable) turns the watch items a reviewer marked "incorporate into database" in that dir's `review_log.jsonl` into tasks: on a tracked plant they join the brief; a candidate new to the tracker is listed under `promoted_new` in the index and in the printout for the scope-wide agent. `--validation` turns each research fix from the report into a unit task (a Data Sources error already on the empty-source list is not repeated); by-hand web UI fixes and coal exceptions stay in the memo. `--ids` adds the ID matcher's tasks (a status, capacity or year that disagrees with EIA-860M, EIP or the Sierra Club list; a Sierra Club row matched to the plant but to no unit) and replaces the two generic EIA "Other IDs" tasks, since the matcher already checked the codes. Update mode is the manual's ladder plus the gap list, not a deep sweep: each unit gets a "What to check" block, the field list shrinks to what the tasks touch, and with the default `--scope ladder` plants with no task are left out (listed under `not_tasked` in `_index.json`; `--scope all` briefs every plant). `--mode blind` is calibration only. Outside the US the two EIA "Other IDs" tasks are not generated.
3. `python build_sweep_args.py --batch ../batches/<tag> --model sonnet --group-max 5` → `staging/sweep_args.json`. Run the scope's permit harvester now, in the background, so every agent starts from the permit index in `work/permits/<tag>/<plant_id>.md`: `python harvest_permits.py --scope germany` for Germany (the register throttles every read; see the Germany note, "Permit register"), `python harvest_permits_iowa.py --scope us-ia` for Iowa, `python harvest_permits_mississippi.py --scope us-ms` for Mississippi (MDEQ's enSearch Online permits and activity since 2021, the public notice page and its Wayback copies, and the Permit Board agendas and minutes; over an hour because the scanned minutes need OCR, `--match-only` for a quick name check; it writes `work/permits/us-ms/<pid>.md` per plant and `_unmatched.md` for power-like facilities GEM lacks, which `docs/coverage/us-ms.json` makes the scope-wide agent answer one by one; a "checked by hand" match is reliable, a "name match" or "same city" match is a lead to confirm). Mississippi also has `python harvest_psc_mississippi.py` (Public Service Commission dockets since 2022: the portal search passes a real-Chrome gate, then curl replays it; the monthly agenda PDFs are the stable citation for a docket's title and filing date; documents and their text stay in `work/psc_ms/`, never committed) and `python pull_queues_mississippi.py` (the MISO queue JSON and the Southern Company queue, read from its Power BI report; the TVA queue is two dated PDFs on TVA's OASIS, read from its menu in real Chrome; save each table as a CSV under `work/tva_queue/` and pass one `--tva-file` per file, and `--match-only` with `--tva-file` swaps the TVA rows of a saved run). Both write to `batches/us-ms/harvest/`, and `build_state_brief.py --harvest ../batches/us-ms/harvest` puts each plant's matched dockets and queue entries on its brief and the unmatched gas and oil items in `briefs/_harvest.md` for the scope-wide agent. A queue entry or a docket title is a lead to a document: cite the docket document or the queue page, and check a docket match against the document, since big filings name neighboring plants. A docket search finds a docket by the year it opened, so an older docket with new filings needs a docket-number search. **Any state or country whose permit portal holds plant documents gets a harvester before its first sweep** (Baird 2026-10-19, after the Iowa sweep missed the Burlington permits): a search form, a session or a paged table is a reason to script the portal, never a reason to skip it. Pick the model at dispatch time (cheapest genuinely good enough); `--group-max N` packs small plants into one agent.
4. Workflow tool: `scriptPath: .claude/workflows/state-sweep.js`, `args` = that JSON as an object. One subagent per group writes `shards/<plant_id>.json` plus a verifier log `shards/<plant_id>.urls.jsonl`; downloads go to `work/sweep_<tag>/`. The prompt carries the US ladder (EIA, ISO queues, state permits) for a state and a country ladder (regulator register, TSO and ENTSO-E, capacity-market registers, permit registers, owner pages, local-language press, with the 20 MW EU and UK threshold) otherwise. In parallel, one Sonnet Agent does the scope-wide search (newly announced gas plants, queue and tender results, the captive LNG block in `briefs/_captive.md`, and for a US state the plans in `briefs/_irp.md`, the data-center block at the end of `_captive.md`, plus any `promoted_new` candidates) and writes `shards/_state.json`: `qa` and `monitor` items, `newplants` and `newunits` for every project GEM lacks that one verified source names with a capacity or none (the add rule at the top of `briefs/_scope.md`, Discovery SOP §3.1, Baird 2026-10-23: a queue entry or planning document is `announced`, a permit application or prior-approval docket `pre-construction`; a gas project in a utility plan, draft included, is flagged `irp: true`; a qualifying terminal from the captive LNG sheet whose generating capacity the sources support is flagged `captive_lng: true` with `checks: [6, 44]`), and `meta.irp_summary` (one plain sentence per utility, for the Notes draft). A `monitor` item new to the tracker names its `watch_case` (seven values in `schema_constants.WATCH_CASES`); gate `watch-case` flags one that names none. It also reads `briefs/_scope.md` and writes `batches/<tag>/coverage.json`: under `sources`, one entry per id in `docs/coverage/<tag>.json`, either `status: "searched"` with `how` (the script, query or pages read) and `found` (what turned up, or that nothing did), or `status: "blocked"` with an `access` note that names the `fetch.py` ladder and the Wayback lookup it tried; under `ids_followup`, one entry per EIA ID the brief lists, with `decision` add, below_threshold, out_of_scope or already_in_gem (plus `gem_plant_id`) and the evidence. Anything noticed along the way is chased to an answer, never parked in a note as "not researched" or "noticed in passing". **Gas-fired data center plants and backup engine fleets are adds** (Baird 2026-10-27, `notes/data_center_backup_plan.md`): the agent reads `briefs/_data_centers.md`, writes a `newplants` record (`checks: [39]`) for every site at the summed nameplate threshold or with generators and unknown capacity, and answers every listed site in `coverage.json` under `data_centers`; gate `data-centers` enforces it. **Data center catch-up batch** (one checklist step for a scope already delivered, built 2026-10-27): `python data_center_fleets.py --state <State> --leads ../work/dc_leads/us-<st>.csv --out-dir ../work/permits/us-<st>-dc` (the lead CSV names every campus the earlier batch noticed, with any permit or news link; a named site with no document on record gets the verdict `no_documents` and a search task), then `python build_state_brief.py --state <State> --mode update --batch ../batches/us-<st>-dc --data-centers ../work/permits/us-<st>-dc/_data_centers.json --data-centers-only`, which keeps only the GEM plants the sites match and records `focus: data_centers` in the index so the `validation`, `ids_followup` and `statewide-coverage` gates step aside. One Sonnet agent reads `briefs/_data_centers.md` and the matched plant briefs, writes `shards/_state.json` and `coverage.json`, then `assemble_state.py`, `state_gate.py` and the review page as usual. A `newunits` or `newplants` item in `_state.json` uses exact export headers in `fields` (`Turbine/Engine Technology`, never `Technology`), keys `refs` by Data Source column (`Capacity Data Source`, `Unit name Data Source`, `Owners Data Source` and so on, as `state_gate.ref_col_for` maps them) with a link for every filled field, and quotes the matching spreadsheet row in `researcher_notes` when the link is an EIA xlsx; the Illinois scope-wide prompt got this wrong and failed four gates (2026-10-09).
5. Check the returned summaries for `shard_written: false` and re-run only those plants (`build_sweep_args.py --plants L...`). Then the location hand-back: `python build_sweep_args.py --batch ../batches/<tag> --location-review --model opus` collects the plants whose shard says `location_needs_review: true` (a site map to georeference, or two candidate sites the cheaper agent would not choose between) into a short second sweep on a top-tier model, with the first agent's notes in the brief. Usually a handful of plants; skip the pass when there are none.
6. `python assemble_state.py --batch ../batches/<tag>`, then rerun `check_existing_links.py` for the scope (the assembler rewrites `staged_updates.json`, and the cached rerun puts the saved-copy records back), then rerun `validation_report.py` for the scope if its file is over a day old, then `python access_audit.py ../batches/<tag> --retry` (step 7), then `python state_gate.py --batch ../batches/<tag>` (must print GATE CLEAN; gate `validation` fails on any validation report item with no answer carrying check 7, gate `access` on any give-up the audit did not retry or that loads now, gate `location` on an exact coordinate with no imagery or parcel confirmation in the note, a point outside the plant's state or country, a move over 2 km with no reason, or a georeferenced map with a poor fit or a missing render, gate `statewide-coverage` on a source in `docs/coverage/<tag>.json` with no searched or blocked entry in `coverage.json`, gate `chase` on any qa note or coverage entry that says a thing was noticed and not followed up, gate `ids_followup` on an EIA plant missing from GEM with no record, no plant-name match and no `ids_followup` decision; the advisory `lead-only` line lists values that rest only on a lead site such as Cleanview, interconnection.fyi, gridstatus.io or GridInfo, which stay yellow), then `qc_checks.py --staged` on every lane file and the normal build (§2 steps 8 to 11; add `--irp ../work/irp_us-<state-slug>.json` to the build for a US state that ran the IRP step, which adds the `irp_box` and `irp_notes_draft` sheets and an evidence section). The assembler marks every record sourced from a plan `irp: true`, writes `staged_newplants.json` only when the scope-wide file staged a new plant, and writes `staging/irp_summary.json` for the Notes draft. **Never rebuild a staging folder that was curated by hand after assembly** (Maryland and New York, October 2026): `python add_checklist_fields.py --staging ../batches/<tag>/staging --csv gem_export_gogpt_scoped.csv` adds the checklist fields (`checks`, normalized `concern_type`, `monitor_reason`, `recheck_by`, `monitor_kind`) in place without touching a record id, value or note. `python add_question_fields.py --staging ../batches/<tag>/staging --list work/qa_rows.json` lists the `qa` records without `question` and `finding`; a cheap model drafts the three fields from each note into `{record_id: {question, finding, recommendation}}`, and `--drafts work/qa_drafts.json --merge` checks every draft against gate `questions`, writes the fields (the old recommendation stays in `recommendation_raw`), folds a scope-wide question into the plant's own one on the same concern, and stamps `meta.question_fields` so the gate is hard from then on (Iowa, 2026-10-27). The advisory `note-drift` line lists units whose database note changed since the brief was built; read each new note and, where a question on that plant answers something else, redraft it with `--drafts` (Iowa, 2026-10-29: the reviewer tied the 430 MW placeholder to Bobcat and Cedar River after the brief printed the note blank). Blind runs also get the calibration memo. Close out with the note's open questions, the roster row and the batch INDEX.md.
7. `python access_audit.py ../batches/<tag> --retry` re-runs every check that failed in the sweep with the current fetch ladder, including every URL an agent gave up on in its `source_log`, tables the failures by host and kind, and writes `<batch>/access_retry.json`. Run it before `state_gate.py`: gate `access` fails on a give-up the audit never retried, on one that now loads, and on any note that excuses a page as a search form, a script or a paged table. Add any host that needed something special to `docs/reference/site_access.md` and the country note's "Site access" section; a sign-in wall goes to Baird with the site name.

## §8 Review a batch (the review app)

Decide on a batch's staged edits one by one before the deliverable is built. Plain-language
guide in `review_app/README.md`. The app never touches the GEM database; its only outputs are
the store spreadsheet's `log` tab and its mirror, the decision log in the staging dir.

Before a delivery note goes out: `python review_app/build_all.py --check`. Rebuild and republish every page it lists as stale or unmarked (`review_app/README.md`, "Keeping every page identical in interface"). Hooks in `.claude/settings.json` run the same check at session start and before a stop.

1. From the repo root: `python review_app/server.py --scope us-md --scope us-ny` (any number of batches; `--dirs` for explicit staging folders, `--reviewer "Name"` to override the git user). The page opens on 127.0.0.1:8767.
2. Work the queue: accept / hold / reject / suggest each change (`a` `h` `r` `s`), calls and notes on the concerns and entity checks, and one of four calls on a watch item (incorporate into database / hold / send to possible updates / remove from watchlist). "Ask the PM" is a checkbox beside any call, with its own filter. The left pane also has a checklist view: the nine QC/Country checklist groups (`review_app/checklist.py`), each a filter, with group 9 opening the close-out panel (draft close-out note, sheet and doc links, IRP boxes to tick on a US page, what the page cannot see). The minor tab (value checked and stands, only a link added) has an accept-all button. Every call is appended at once to the store spreadsheet's `log` tab (`review_app/ledger.py`; a store that cannot be written refuses the call) and then to `batches/<scope>/staging/review_log.jsonl`; `review_decisions.json` is the derived latest-per-record copy. Both sidecars are tracked and committed with the batch; `python review_app/pull.py` catches a clone up from the store.
3. Build from the calls, from `scripts/`: `python build_review_package.py --staging-dir ../batches/us-<st>/staging --scope us-<st> --mode update --decisions`. Only accepted edits reach the actions workbook; held, rejected, suggested and undecided edits are listed at the top of the evidence file with the reviewer's note, and items carry their call. The workbook opens on `checklist_summary` (counts per checklist group and row), splits the watch list into `watch_new_to_tracker` and `watch_existing_plants`, and adds `promote_to_database`, `possible_updates_rows` and `questions_for_pm` from the calls (`docs/reference/workbook_conventions.md`). A build without `--decisions` ignores the log and says so.
4. Suggestions go back to the researcher (a follow-on sweep or a hand edit of the shard, then `assemble_state.py` again). Watch items marked "incorporate into database" become tasks in the next batch through `build_state_brief.py --promote <staging dir>` (§7 step 2). The `record_id` is stable across rebuilds, so the log still applies.
5. Colleague without the repo: `python review_app/build_static.py --scope us-md --scope us-ny --reviewer "Name" --export-csv scripts/gem_export_gogpt_scoped.csv` writes one html file under `work/`; send it, they review in a browser and press "download decisions", then `python review_app/import_log.py <their file> --reviewer EMAIL` appends the calls to the store `log` tab and the staging logs (safe to re-run) and step 3 builds as usual. The reviewers' normal surface is the claude.ai artifact page (published from the work profile only; capabilities `db`, `downloads`, `user`; reviewer invited by email as editor): it saves the calls to the artifact's database as they are made, its "push to log" button asks for a sync, and `import_log.py --reviewer EMAIL` takes the `logs/<viewer id>` documents read with ArtifactData (`list` with `out_dir`). Live pages, rules and the sync-back recipe in `review_app/README.md`.
